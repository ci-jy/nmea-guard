# Cortex-M3 build on QEMU

```
make -C firmware qemu-test     # build, run the vectors on QEMU, print the size report
make -C firmware size          # size report only
```

It needs `gcc-arm-none-eabi`, `libnewlib-arm-none-eabi`, `libstdc++-arm-none-eabi-newlib` and `qemu-system-arm`. The library sources in `src/` are compiled unchanged with `-mcpu=cortex-m3 -mthumb -Os -fno-exceptions -fno-rtti -Werror` and the same warnings as the host build. On ARM `char` is unsigned, so `-Wconversion` sees different code than on x86, and it still builds clean.

## What's in `firmware/`

| file | what it does |
|---|---|
| `mps2_an385.ld` | linker script for QEMU's `mps2-an385` (Cortex-M3, code at 0, RAM at 0x20000000), 16 KB stack |
| `startup.c` | vector table and reset handler: copy `.data`, clear `.bss`, run constructors, call `main()`. Every fault handler prints and ends the run |
| `semihost.cpp` | ARM semihosting over `bkpt 0xAB`: print text, exit with a status QEMU passes on |
| `cxx_support.cpp` | replaces libstdc++'s `__throw_out_of_range_fmt` with a trap (see below) |
| `runner.cpp` | the test-vector runner |
| `vectors.inc` | 797 test vectors, generated by `scripts/gen_vectors.py` |
| `probe.cpp` | size probe: UART polling loop feeding a static Parser |
| `host_io.cpp` | stdio version of the runner's I/O, so ctest can run the same runner on the host |

## The test vectors

`scripts/gen_vectors.py` picks four decoded sentences and one other per gpsd log (seed 1), and for each decoded one adds a copy with 1 to 3 bytes dropped or 1 to 2 bits flipped, using the same functions as `tools/corrupt.py`. The expected outcome of every line comes from `tests/nmea_reference.py` and the expected values from pynmea2, so nothing on the C++ side decides what's right. Lines that aren't a single printable sentence are left out because their outcome depends on what comes before them, which the host tests already cover.

The current file has 114 GGA, 121 RMC, 102 GSA, 44 VTG, 101 other and 315 rejected lines. `tests/test_vectors.py` regenerates it from the logs and fails if the committed copy differs.

The runner feeds every vector to one `Parser`, a byte at a time, followed by CR/LF, the way a UART interrupt would. Each line has to produce exactly one event of the expected kind, and for decoded sentences the time, up to four numbers and two integers have to match. Numbers are allowed to differ by 1e-12, the same tolerance as the host differential test. In practice all 1,262 matched bit for bit. The Cortex-M3 has no FPU and libgcc's soft-float routines round the same way SSE does on x86.

After the vectors come four scenarios: a 300-byte line that overflows the buffer followed by a good GGA, a `reset()` halfway through a sentence, the head of a GGA running into a whole RMC, and a GGA + RMC epoch closed by the next GGA. Then the runner paints 8 KB of stack below its frame, feeds every vector again, and counts how much of the paint was overwritten.

The run ends through semihosting `SYS_EXIT_EXTENDED`, so QEMU's exit status is the runner's and `make` fails if any vector does. QEMU runs under `timeout 120` in case something hangs.

## Size

The flash and RAM figures don't come from the runner, which carries 90 KB of vectors. They come from `probe.cpp`, which is about the smallest firmware that actually uses the parser: it polls the board's CMSDK UART, feeds each byte to a static `Parser` and stores the last valid latitude and longitude. `scripts/firmware_report.py` reads its linker map and assigns every kept input section to the library, libgcc, newlib or the probe itself. The result goes to `firmware/build/firmware-size.json`, and the committed copy is `results/firmware-size.json`.

| | flash | RAM |
|---|---:|---:|
| nmea-guard library | 4,872 | 0 |
| libgcc soft-float (double add, multiply, divide, compare) | 2,220 | 0 |
| newlib-nano (`memcpy`, `memchr`, `memcmp`, `memset`) | 620 | 0 |
| startup, UART loop and the `Parser` object | 525 | 1,152 |
| total | 8,237 | 1,152 |

Of the library's 4,872 bytes, `sentences.cpp` (the four decoders) is 2,458 and `fields.cpp` 1,392. The framer is only 342. `sizeof(Parser)` is 1,136 bytes on the Cortex-M3, a little less than the 1,144 on x86-64 because of `size_t` padding. Feeding all the vectors used 1,016 bytes of stack, and that includes the runner's own two frames around `feed()`.

These numbers are from arm-none-eabi-gcc 14.2.1. Other versions give somewhat different sizes; CI uses Ubuntu's package and only checks that the run passes.

## Things I found

- **The library pulled in `abort()`.** `std::string_view::substr` checks its position and, even with `-fno-exceptions`, refers to libstdc++'s `__throw_out_of_range_fmt`. That drags in `abort()`, newlib's signal code and `_sbrk`, so the first link failed with undefined `_kill`, `_getpid` and `end`. The parser never passes a position past the end, so `cxx_support.cpp` replaces the helper with a trap. Without it, a firmware build that uses newlib's stubs would quietly link a heap. `scripts/firmware_report.py` now fails if `malloc`, `free`, `_sbrk`, `abort`, `__cxa_throw` or `operator new` show up in the probe.
- **No double maths in hardware.** More than a quarter of the probe's flash is libgcc's soft-float. Parsing decimals as integer mantissas would get rid of most of it but change the API. I left it, see the README.
